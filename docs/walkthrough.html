01

What this application does

Pyramid is a workspace for tracking tasks and projects. A user signs in, sees their tasks grouped by status, and moves work through four stages. The same data is presented two ways — grouped tables and Kanban columns — and every task opens into a detail page carrying description, labels, subtasks, comments and an activity feed.

The governing design goal is that nothing is a local-only illusion. Every visible control writes through to the database. Change a priority in a dropdown, reload the page, and the change is still there. Section 11 records the test run that proves this for all 21 interactive paths.

02

Architecture

Two packages — a Next.js frontend and a NestJS API — talking REST, with MongoDB Atlas for storage. Requests cross three gates before touching data: token verification, DTO validation, then the service layer.

Decisions worth naming

One grouped endpoint feeds both views. GET /api/tasks/grouped returns tasks already bucketed by status. List and board render the same payload, so the two can never disagree, and switching between them costs no request.

Mutations re-fetch instead of patching local state. Every write calls the API then reloads the grouped payload — trading a little latency for the guarantee that what you see is what the database holds.

The vocabulary is defined once per side. Four statuses, five priorities, declared in constants.ts and enforced at the validation boundary. Note the deliberate casing split: statuses are Title Case ("To Do"), priorities lowercase ("high").

Theming is two independent axes. data-theme and data-accent are separate attributes driving CSS custom properties. No component hardcodes a colour.

03

Authentication

Continue as Guest calls POST /api/auth/guest, which creates a throwaway user document and returns a signed JWT. The token lands in localStorage; on each subsequent load AuthProvider resolves it via GET /auth/me. An expired or revoked token is discarded and the app falls back to anonymous rather than erroring.

Each guest login creates a distinct user, so two people testing never share a board.

Google sign-in

The Google button runs the OAuth 2.0 authorization-code flow and ends in the same kind of session token. The token comes back in a URL fragment rather than a query string — fragments are never sent to a server, so it stays out of access logs and Referer headers.

The CSRF state is an HMAC signed with JWT_SECRET rather than a server-side session, so the flow survives a restart or a second instance. Accounts match on Google’s stable subject id rather than email, and an unverified email is never used for matching — otherwise an account could be claimed by signing up with its address.

Where credentials are not configured, GET /auth/providers reports it and the UI hides the button, so the app runs guest-only rather than offering a control that fails on click.

04

The task list

The default landing view. Tasks are grouped into one table per status, each with its own header and its own Add Task affordance. Priority renders as a coloured glyph plus label, the colour carrying the semantics.

Inline creation. Add Task opens a text field in place; Enter creates the task in that group's status with a due date defaulted one week out, so a new row is never missing a date.

Row actions. The ⋯ menu exposes priority, status and delete. Changes write immediately and relocate the row if its group changed.

05

Board view

The same four statuses as columns, each showing a count. Cards surface more than list rows do: assignee, a due-date chip, and labels as individual chips. The due-date chip carries a red-tinted background — this design treats due dates as attention-carrying, not neutral metadata.

06

Search and filtering

Fields carries both the List/Board switch and per-column visibility.

Search opens from the magnifier or ⌘F / Ctrl+F, intercepted so the app's search opens instead of the browser's. Input is debounced, and filtering runs client-side against the already-grouped payload, so results are instant.

07

Task detail

A two-column layout: content left, Details panel right. Title and description are click-to-edit, saving on blur — there is no save button because the design shows none.

Subtasks reuse the same table component as the main list, so editing behaves identically at both levels. Comments support threaded replies; the composer retains its text if a post fails. Updates shows a server-recorded activity feed.

08

Projects

The same table shell as tasks, with Priority, Lead and Due Date. Each project opens to a detail page listing that project's tasks — the task list scoped by projectId.

09

Settings and theming

Profile fields save on blur through PATCH /api/users/me, verified to survive a reload. Theme switches light/dark; Color picks among six accents.

Dark mode is a genuine re-themed palette rather than an inversion — surfaces, borders, table headers and priority colours all carry separate dark values, with priority tones brightened for contrast.

The validation boundary

A global ValidationPipe runs with whitelist and forbidNonWhitelisted, so an unknown field is a 400 rather than a value that silently does nothing. Errors flow through AllExceptionsFilter into a consistent shape, and the client's ApiError carries the status code so callers can tell 401 from 400.

Part A — Implemented

8 items

Shipped and verified against the running application.

A1 · Defect found during walkthrough — implemented

The comments section was labelled “Subtasks”

On task detail, the comments heading repeated the label of the subtask table directly above it. The surrounding code comment already read {/* Comment thread */}, confirming the label was wrong rather than intentional.

task-detail-view.tsx:368 — Changed: the heading now reads “Comments”. Verified against the live DOM: exactly one Subtasks heading and one Comments heading.

A2

Board drag-and-drop

Implemented
Cards move by pointer drag from the grip handle, with a target-column highlight, drop-zone hint and cursor ghost — built on Pointer Events, since HTML5 drag-and-drop gives no usable touch drag and no keyboard path. A full keyboard equivalent ships alongside: Space to pick up, ←/→ to move, Space to drop, Esc to cancel, with aria-grabbed and a live region narrating the target. Verified: a card picked up, moved and dropped into the adjacent column.
A3

All seven filter axes functional

Implemented
Previously only Priority worked; the rest opened empty submenus. Status, Priority, Members, Due Date, Teams, Labels and Reporter now all filter — axes combine with AND, values within an axis with OR. Options derive from the loaded payload, so the menu only offers values that exist. Teams correctly reports “No teams”: the API has no teams field, so an empty state is the truthful rendering.
A4

Duplicate “Members” label

Implemented
Two Fields entries shared a label while toggling different columns. The second is now labelled “Assignees”.
A5

Undo on delete

Implemented
Deletions raise a toast with a six-second undo, recreating the record with its original priority, due date, members and labels — less interruptive than a confirmation dialog, and it recovers the more common regret. Known incompleteness: undo does not restore subtasks or comments — see D1 below.
A6

Mutation failures surfaced

Implemented
The change handlers previously awaited without catching, leaving a failed request unexplained. Every mutation now reports failure through a danger toast naming the action.
A7

Loading skeletons

Implemented
Table, board, projects and detail skeletons render at the real row heights, so arriving content does not shift the layout — most visible during the ~20s Atlas cold start.
A8

Focus rings and drawer focus trap

Implemented
A single :focus-visible treatment now covers links, buttons, menu items and inputs — keyboard only. The mobile drawer is a true role="dialog" with aria-modal, trapping Tab and restoring focus on close. Verified: ten consecutive Tab presses stay inside the drawer.

Part B — Defects identified, not yet fixed

3 items

Found in the second review pass. Two of these silently destroy user data.

D1

Undo does not restore subtasks or comments

Open · high
Deleting a task cascade-deletes its subtasks, comments and activity server-side (tasks.service.ts:171). The undo introduced in A5 recreates only the parent task, so its children are permanently lost even though the UI implies a full restore. Suggested: either a restore endpoint that soft-deletes and revives the whole subtree, or narrower toast wording. The current behaviour promises more than it delivers, which is worse than offering no undo at all.
D2

Bulk delete has no undo and is not atomic

Open · high
The column header menu offers “Delete all (N)”, which loops over tasks firing a separate DELETE per card. Nothing confirms, nothing undoes, and a failure halfway leaves the column partially deleted with no indication of which succeeded. Suggested: a bulk endpoint deleting in one operation, with the same undo affordance as single deletes.
D3

No optimistic-concurrency control

Open · medium
Two people editing the same task both PATCH it and the last write silently wins — the first change disappears with no warning. updatedAt is already returned but never checked on write. Suggested: accept a version field and return 409 Conflict on mismatch. Worth doing only if multi-user editing is a real scenario for this product.

Part C — UX gaps identified

5 items

Rough edges that do not lose data but noticeably affect the experience.

U1

Errors offer no way to recover

Open · medium
A failed fetch renders its message as static text with no retry, so the only recovery is a full page reload. Suggested: a “Try again” button calling the existing reload() — the hook already exposes it, making this a small change with real payoff on flaky connections.
U2

Empty states are a bare sentence

Open · medium
An empty board shows only “No tasks yet.” — no illustration, no explanation, no call to action, on a new user’s very first screen. Suggested: pair it with a primary “Add your first task” button, and offer “Clear filters” on the filtered variant.
U3

View mode and filters do not survive a reload

Open · medium
Board/List choice, active filters and column visibility are all component state, so a refresh resets everything. Suggested: persist view and field visibility to localStorage, and reflect search and filters in the URL query string — which also makes a filtered view shareable.
U4

No custom 404 or error boundary

Open · medium
A non-existent task shows Next.js’s default not-found page, carrying none of the app’s design; an uncaught render error shows a blank page in production. Suggested: app/not-found.tsx and app/error.tsx using the app shell, the latter with a reset button.
U5

Task titles have no length feedback

Open · low
The API rejects titles over 200 characters, but no input enforces or signals the limit, so a long title is accepted by the field and rejected on save. Suggested: maxLength plus a counter as the limit approaches.

Part D — Polish and hardening

4 items

Lower-urgency work, plus what should be done before the deployed link circulates.

P1

Optimistic UI

Deferred
Every change round-trips before the UI updates — imperceptible locally, sluggish on a slow connection. Not implemented deliberately: optimistic updates only help with proper rollback, and a half-built layer that silently diverges from the database is worse than the current behaviour, which is correct if not fastest.
P2

Board columns do not scroll independently

Open · low
Each column grows with its content, so one long column stretches the board and pushes the others’ “Add Task” far down the page. Suggested: a max-height with per-column overflow.
H1

No rate limiting on guest login

Open · high
POST /api/auth/guest writes a user document per call and is unauthenticated, making it trivially abusable on a public URL. This is already measurable: the development database holds 80 users, 70 of them guests (88%) — accumulated from testing alone. A free M0 cluster would fill quickly under real traffic. Suggested: @nestjs/throttler on the auth routes plus a scheduled job pruning old guest accounts; neither exists today.
H2

Missing security headers; pagination unused

Open · medium
No helmet — a one-line addition supplying standard security headers. Pagination exists but is unused — the API supports skip/take capped at 100, but the UI never paginates, so a board past 100 tasks silently truncates with no indication rows are missing.

14

Known limitations

Design comparison against the Figma source was not performed. The Figma file for this assessment could not be opened with the access available during development. This document therefore describes the implementation as built and verified; it makes no claim of pixel-level equivalence to the Figma design, and no measurement audit was carried out.

Some detail-header controls are presentational. Lock, watcher count and share render per the design but are not wired to behaviour.

Atlas cold start takes roughly 20 seconds. Mongoose logs one retry before connecting. Harmless locally, but a platform with a short startup healthcheck could fail on it.

No unit test suite. jest finds no .spec.ts files; coverage comes from the end-to-end harnesses. npm test in the backend exits non-zero on an empty suite.

cd backend
npm install
npm run build
npm run start:prod          # http://localhost:4000/api

# Frontend — needs frontend/.env.local with NEXT_PUBLIC_API_URL
cd frontend
npm install
npm run build
npm start                   # http://localhost:3000
